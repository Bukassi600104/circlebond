1. **Other users' memberships make an existing user's circles disappear** (`dataconnect/bondcircle/queries.gql:108`, `server/repositories/dashboard.ts:60`, `app/api/v1/circles/[id]/route.ts:87`).
   - **What this is:** The shared dashboard repository supplies the web dashboard and both native circle read endpoints. It executes `GetDashboardCircles` without variables, then filters the returned global membership list by the requesting user.
   - **Problem:** The query has no user filter or explicit pagination. Data Connect generated list fields default to 100 rows, so a user's sole older membership disappears after 100 newer memberships belonging to other users; native detail returns 404 for that user's legitimate circle. The same truncated global list also replaces the authoritative member count with a partial count at `server/repositories/dashboard.ts:94`.
   - **Fix:** Bind the authenticated user ID in the shared connector query and fetch that user's complete membership set with bounded pagination. Retain the authoritative circle member count instead of counting a truncated global list; update the shared caller and add regressions with at least 101 unrelated memberships and more than 100 memberships for one user.
   - **If we skip it:** Normal growth silently removes circles from existing users' dashboards and makes valid native deep links report that their circles do not exist.

This defect predates the remediation diff but is in the connected source/caller scope of this final readiness review. The [official Firebase query-definition reference](https://firebase.blog/posts/2025/05/dataconnect-queries-defs-to-client-code) shows the generated list signature `limit: Int = 100`. An independent assert-based probe executed the actual transpiled repository against the documented newest-100 connector response: 101 synthetic memberships, the requesting user's sole row older than the other 100, no query variables, resulting `[]`. The probe exited 0 after confirming the failure case; this is a controlled module reproduction, not a fresh database run. No product fix was authored by this reviewer.

2. **A successful retention purge leaves private receipts behind** (`dataconnect/bondcircle/queries.gql:2925`, `server/repositories/retention.ts:147`, `server/repositories/retention.ts:170`).
   - **What this is:** After the retention period, the repository enumerates receipt image paths, deletes the corresponding Storage objects, then deletes sensitive database records and marks the circle purged.
   - **Problem:** `GetCircleRetentionPayload` fetches receipts without pagination, so only the default first 100 are enumerated. With 102 receipts from one member, the latest membership pointer adds receipt 102 but misses receipt 101; the final mutation deletes every receipt row and reports completion while that private file remains. Subsequent purge jobs skip the purged circle, and the database no longer records the missing image path. Invitations use the same unpaginated enumeration before acceptance deletion.
   - **Fix:** Read the complete ordered receipt/path and invitation sets with bounded pagination before removing metadata. Fail closed if complete enumeration cannot be established, and add a regression with more than 100 receipts whose omitted older image is not the latest membership pointer.
   - **If we skip it:** The advertised retention cleanup can permanently retain sensitive receipt images while falsely recording that cleanup finished; the normal retry path has lost the records needed to find them.

Independent assert-based execution of the actual `purgeEligibleCircle` module confirmed the 102-receipt case: returned `completed`, reported 101 files deleted, called the all-record metadata purge and left one synthetic private file in the controlled Storage fixture. Exit 0 confirms the reproduced defect, not product correctness. No real Storage or database operation ran. This is another pre-existing connected-source defect; it is not closed by the small synthetic purge scenario in the earlier database suite.

3. **New receipts hide an earlier member's payment evidence** (`dataconnect/bondcircle/queries.gql`, `GetContributionWorkspace.receipts`; `server/repositories/contributions.ts:95`).
   - **What this is:** One shared workspace supplies members' payment history and pending sums, receipt replacement, organizer review and private image lookup.
   - **Problem:** The query returns only the newest default 100 circle receipts before the repository filters by uploader. An older own pending receipt disappears after 100 newer receipts from others, its pending amount becomes zero, and the omitted rejected receipt/image cannot be found for replacement or retrieval. More than 100 receipts is valid in a circle with at most 100 joined members because partial payments and replacement history are retained.
   - **Fix:** Fetch the complete ordered receipt collection with bounded paging in the shared repository, keeping failures on later pages fatal. Preserve the existing viewer/role filters and signing checks; add a regression whose older own receipt falls outside the first page.
   - **If we skip it:** Members lose payment history and see incorrect pending summaries; legitimate evidence and replacement/review actions disappear as other members contribute.

4. **Old live invitations lose organizer controls after newer history accumulates** (`dataconnect/bondcircle/queries.gql`, `GetCircleInvitations`/`GetInvitationAcceptances`; `server/repositories/invitations.ts:136`, `server/repositories/invitations.ts:281`).
   - **What this is:** Shared invitation loaders supply the organizer list, live seat reservations, revocation and approval; acceptance history also decides whether a user already responded.
   - **Problem:** Both lists silently stop at the default 100. An older live link falls outside 100 newer revoked/expired records, so its organizer receives `Invitation not found` when revoking it and its outstanding capacity is omitted from reservations. Open-link declines and pending approvals can also exceed 100 without exceeding the joined-member plan limit, hiding later responses from approval/duplicate-response checks.
   - **Fix:** Paginate both shared ordered loaders completely before reservations or state lookup, and fail closed on later-page errors. Keep circle ownership and transition checks; test revocation of an older live invitation and approval of a pending response beyond page one.
   - **If we skip it:** A live link can become unavailable to normal organizer revocation, and valid membership requests become unreachable or incorrectly treated as new.

Independent actual-module probes confirmed findings 3–4 against the documented default page: own receipt list empty/pending amount zero, and old live invitation revocation refused with zero mutation. The corrected probe exited 0. An initial harness assertion compared objects from different VM realms and failed on their prototypes; comparing serialized request metadata fixed the harness without changing application source or the reproduced outcomes.

5. **Pending membership rows can hide an admitted user's role** (`dataconnect/bondcircle/queries.gql`, `GetCircleEngineRecord`, Gift/Aso-Ebi/Support detail, contribution workspace and communication membership lists; `server/repositories/circles.ts:171`).
   - **What this is:** Core repositories select all membership statuses, then find/count only `joined` rows in JavaScript after the connector's default 100-row page.
   - **Problem:** The existing Gift member route creates `invited` membership rows, while its availability and shared capacity counts count joined members only. Pending rows can therefore exceed the plan's joined-member ceiling, fill the first page and exclude a later genuinely joined user; role lookup returns null and circle workspaces refuse access even when there are fewer than 100 joined members.
   - **Fix:** Filter these authorization/detail membership queries by `membershipStatus: joined` before the list limit, matching every current consumer's existing filter. Keep a separate complete pending-membership query where a pending-membership UI actually requires it; do not raise the approved plan limits.
   - **If we skip it:** Users who have been admitted to an ordinary circle can fail role checks and lose access because unrelated pending memberships occupy the query page.

An independent actual `FirebaseCircleStore` probe with the first page occupied by pending rows confirmed null for a later admitted user and an incomplete joined count. Current approved catalogue limits remain **3/10/30/100**, as confirmed in `lib/circle-pricing.ts`, `server/pricing/entitlements.ts` and `docs/MODEL_SPECIFIC_PRICING.md`. No 500-member plan is assumed or proposed. `GetCircleLifecycleSummary` and `GetNotificationContext` already filter joined rows before the limit, so their 100-row default fits the present joined-member contract.
