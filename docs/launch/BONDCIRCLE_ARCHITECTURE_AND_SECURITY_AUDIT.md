## Architecture and scope

The existing Next.js/React application, Vercel hosting, Firebase Authentication, Firebase Data Connect/PostgreSQL and server-controlled Firebase Storage remain the architecture. No backend, database, product mode, pricing catalogue or permission model was replaced. Browser sessions use HTTP-only cookies; native requests verify Firebase ID tokens. Privileged Data Connect operations use server repositories; the user-scoped profile operation binds its key to `auth.uid`.

## Boundary evidence

Additional verified finding F-SEC-007 (High under misconfiguration): challenge and private-file key derivation accepted any nonempty production secret, despite the documented 32-byte requirement. `server/auth/security.ts` and `server/uploads/private-access.ts` now reject keys below 32 UTF-8 bytes in production. Tests cover missing/short keys, the byte-length boundary, explicit private-key precedence and preserved local defaults. Runtime regressions PASS; independent implementation review remains PENDING REVIEW. Length does not establish entropy: operators must still generate random secrets.

- Runtime tests execute the actual transpiled mutation guard: an arbitrary Bearer header fails without origin/CSRF; a verified Bearer principal remains supported; session requests need both same-origin metadata and matching tokens.
- Runtime tests execute both OTP request handlers and the shared sender. A production development-mode setting cannot send/log a development code; neither route publishes a development code even if its sender is stubbed to return development delivery. Correct production configuration invokes the transport; local preview remains functional without credential logs.
- Runtime tests exercise actual receipt-role rules and private-file signing/verification. Another member cannot review/view another uploader's receipt; signed access is viewer, circle and resource bound, expires, and rejects tampering. These are deterministic boundary tests, not authenticated Storage acceptance.
- Existing Storage rules deny direct client access. Upload sanitization decodes and re-encodes approved raster formats with byte/pixel limits and stripped metadata. Actual bucket operations remain blocked by the current production 404.
- Named invitation responses take contact identity from the verified session, not from request-supplied profile fields. Invitation repositories retain token hashing and server authorization. Existing concurrency and emulator evidence must be rerun on the integrated release.
- Session/native authentication verifies Firebase revocation and persisted suspension. Owner access and receipt repositories have explicit role checks. Full cross-user database/Storage exercises are still required against approved staging identities.
- Tracked-file name/marker checks did not reveal a private-key, GitHub-token or live-secret marker; this is a bounded source check, not a complete historical secret scan. Environment templates are tracked; actual environment/private-key files remain ignored. No secret values were printed.
