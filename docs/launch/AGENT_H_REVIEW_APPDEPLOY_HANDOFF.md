H read the corrected parent paragraph, including its quota/cost caveats and no-purchase statement. These are dated published terms, not a workload estimate or guaranteed commercial agreement. Account plan/credit balances were not independently re-requested by H.

The native handoff appropriately retains one authoritative backend, Firebase ID-token verification, secure refresh credentials, server-side pricing/roles, private validated uploads, canonical HTTPS invitations and explicit staging-origin controls. A future browser prototype cannot bypass CSRF/cookie rules; a native client must not send the OTP custom token directly as an API bearer token. The versioned API's missing mutation families are explicitly future work and do not by themselves block web stabilization.

Official [push setup](https://docs.expo.dev/push-notifications/push-notifications-setup/) requires permissions, platform credentials, implementation and supported-device testing. Expo remains a candidate; neither SDK support nor token persistence is accepted as native build or push-delivery readiness.

Not checked: prototype performance/comparison, cross-origin implementation, source export in practice, real FCM/APNs delivery, signing/store accounts, native binaries, physical devices, production migration and provider contract/support guarantees. No prototype is required to support the documented DEFER decision. Future experiments still need approved staging/test identities and owner authorization before public publication or paid use. Risk: low for the assessment itself; native delivery and any new hosted frontend remain separate unstarted/unverified work.
